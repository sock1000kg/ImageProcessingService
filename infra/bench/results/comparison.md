## Final comparison

Runs of 22 Nov 2026, engine image `6b5c9b1`, web `:main`, both at 1280 px (the modes' own size):
**Fast** = `yolo26n-1280-e5-dashcam` (face 0.17, plate 0.11), **Max privacy** = `yolo26s-1280-e5-dashcam` (face 0.06,
plate 0.05). Run list and what each run is for: `docs/report-material/bench-reruns.md`.

How to read the runs:

- **Preloaded** runs hold the workers at 0, queue every image, then release them. Only their **drain** counts (how fast
  N workers empty a full queue, uploads excluded). Their end-to-end number adds uploads and worker start-up one after
  the other and means nothing; ignore it.
- **Warm** runs have N workers Ready and warmed up before the first upload; **autoscale** runs start from 0 (or 1).
  Compare deployment modes on the **end-to-end** of these two only: same uploads, so the gap is start-up and scale-up.
- `processingTimeMs` (p50) is the engine's own time per image (download excluded), so it is free of network and web.
- `web` is limited to 1 CPU (the deployment's setting) unless a row says otherwise. The laptop's preloaded runs use
  4 CPU so web does not cap the workers' drain.
- Differences under about 10 % are noise.

### Laptop (RTX 3050), 3 workers, 3,726 images

| | Fast | Max privacy |
| --- | --- | --- |
| **Drain**, preloaded, web 4 CPU | **1,646 img/min** | **1,232 img/min** |
| Processing p50 / p95 | 61 / 207 ms | 103 / 242 ms |
| Drain with a face whitelist (1 reference photo) | 309 (p50 310 ms) | 262 (p50 314 ms) |
| Drain with a plate whitelist (2 plates) | 392 (p50 66 ms; plate images 1.6 s) | 309 (p50 106 ms; plate images 1.7 s) |
| **End-to-end, 3 warm workers** | **1,421** | **1,197** |
| End-to-end, autoscale 0→3 | 1,323 (−7 %) | 1,015 (−15 %) |
| Cold start (first worker Ready) / back to 0 | 11.4 s / 117 s | 11.2 s / 118 s |

- Fast is about 1.34× Max privacy in drain (61 vs 103 ms per image).
- **Whitelists cost 4 to 5× on the GPU.** Only YOLO runs on the GPU: face alignment (YuNet, OpenCV) and embedding
  (ArcFace, ONNX Runtime with `CPUExecutionProvider`) and plate OCR (RapidOCR, ONNX Runtime CPU) run on the worker's
  CPU, limited to 1 CPU per worker. With a face whitelist almost every WIDER image slows down (crowds, every face is
  embedded); with a plate whitelist the face images barely change and the plate images take about 1.6 s (each detected
  plate is read). The face-whitelist Fast run lost about one minute to a disk spike on the laptop (≈ 3 to 5 % of drain).
- **Scale-to-zero costs 7 % (Fast) and 15 % (Max privacy)** end to end on the GPU: KEDA notices the queue, the first
  worker is Ready after about 11 s, and the run works with 1 or 2 workers until the third arrives. Max privacy pays more
  because a new worker preloads Fast's model (`YOLO_MODEL_NAME`, default `yolo26n-1280-e5-dashcam`), so its first Max
  privacy job swaps to YOLO26s (the run's slowest image: 15 s). The workers are back at 0 about 2 minutes (the 120 s
  cooldown) after the last job.

| | Fast | Max privacy |
| --- | --- | --- |
| Drain, preloaded | 85 img/min (p50 1.05 s) | 35 (p50 2.99 s) |
| Drain with a face whitelist | 61 (p50 1.43 s) | — |

- Max privacy costs about 3× Fast per image on the CPU (2.85 vs 0.96 s warm; drain 35 vs 85 img/min), against 1.7× on
  the GPU.
- **Whitelists cost +23 to 36 % per image on the CPU** (plates / faces): everything already runs on the CPU, so the
  embedding and OCR only add to it.
- **Scale-to-zero costs more on the lab than on the GPU for Fast** (−35 %): 11 s of start-up and the ramp from 1 to 2
  workers are a large part of a run of about one minute. For Max privacy, whose run is 2.5× longer, it is −11 %.
- End-to-end here includes uploading 100 images from the laptop over Tailscale through `kubectl port-forward`, the same
  in every run, so lab runs compare with each other but the absolute numbers are specific to this setup.
- The first preloaded lab runs (16:51 to 17:00) were about 2× slower per image than the same images in the warm run
  (load on the node right after web's restart) and were rerun.

### How `web`'s CPU limit caps throughput (laptop, 3 warm workers, end-to-end)

| `web` CPU limit | Fast | Max privacy |
| --- | --- | --- |
| 0.5 | 1,010 img/min | 1,006 |
| 1 (deployed) | 1,421 (+41 %) | 1,197 (+19 %) |
| 2 | 1,481 (+4 %) | 1,174 (−2 %) |

Processing time per image is the same at every limit (Fast 61 to 65 ms, Max privacy 102 to 104 ms), so the differences
are all in `web`: it receives every upload (one request per image, written to MinIO and Postgres) and records every job
event in the same Node process (`web/docs/backend-throughput-notes.md`). At 0.5 CPU web caps both modes at about
1,000 img/min and hides the difference between the models. From 1 CPU the workers set the pace: Fast gains another 4 %
at 2 CPU, Max privacy nothing. On the lab the workers are the limit long before web (97 img/min at most).

### Against deface

database (runs of 5 Nov, unchanged). Accuracy from `engine/training/detection/bench/comparison.md` section C, every tool
at deface's precision at its default threshold (face precision 0.643).

| Tool | Speed (img/min) | Face privacy, all faces | Faces ≥ 16 px | Plates |
| --- | --- | --- | --- | --- |
| **Fast**, 3 workers | **1,646** drain, 1,421 end-to-end | **0.803** | **0.933** | **0.988** |
| **Max privacy**, 3 workers | **1,232** drain, 1,197 end-to-end | **0.828** | **0.947** | 0.978 |

- Against deface at full resolution, Fast gets through 2.7× as many images and Max privacy 2.0×, while hiding 8 to 10
  points more of all faces at the same precision, and blurring plates too.
- Per process it is about even or slower: one of our workers does about 550 (Fast) or 410 (Max privacy) img/min,
  against one deface process at 614. The lead comes from running 3 workers on one GPU, and our numbers include the
  queue, object storage and database that deface doesn't have.
- deface at 640×480 is faster than both (1,871), but hides 0.54 of all faces against 0.80 to 0.83.
