## Final comparison

Runs of 5 Nov 2026. Models: **Fast** = YOLO26n (`yolo26n-1280-e20-crowd.pt`, threshold 0.17), **Accurate** = YOLO26s
(`yolo26s-1280-e5-plates-frozen-x3.pt`, threshold 0.13), base = YOLOv8n-oiv7 (threshold 0.35). The engine has one threshold
per run so far, so these are the face thresholds. **Drain** = how fast the workers empty a full queue, uploads excluded;
**end-to-end** = first upload to last result. `processingTimeMs` (p50) is the engine's own inference + blur per image.
Differences under about 10 % are noise.

### Lab (`home-server`, CPU only), `web` at 0.5 CPU, 100 images

| Model | Input | Drain, 2 workers | End-to-end, 2 workers | Autoscale 0→3 (end-to-end) | Processing p50 |
| --- | --- | --- | --- | --- | --- |
| Base (control) | 640 | 81 img/min | 42 | — | 0.90 s |
| Fast | 960 | 98 | 58 | 115 | 0.73–0.78 s |
| | **1280** | **73** | **40** | **84** | **1.03–1.04 s** |
| Accurate | 960 | 68 | 50 | 70 | 1.45–1.49 s |
| | 1280 | 33 | 28 | 53 | 2.5–3.4 s |

- The lab is limited by its **workers**, not `web`: in the fixed runs the workers spend about 90–95 % of the time
  processing (Fast at 1280: 147 s of processing in 82 s across 2 workers; Accurate at 1280: 350 s in 184 s). `web` handles
  far fewer images per minute here than it can. Raising its limit would not change these numbers much.
- End-to-end with 2 fixed workers looks low because the clock also covers 20 s of uploads over Wi-Fi and the wait for the
  workers to start (30–70 s of a 100-image run). Autoscale starts sooner and adds a third worker, so it finishes about
  1.5–2× faster.
- Fast at 1280 keeps the old base model's lab speed at 640 (40 vs 42 img/min) with far better accuracy. Accurate at 1280
  is about 1.5–2× slower than Fast at the same size.

### How `web` is a bottleneck (laptop)

Same cluster, engine and settings; only `web`'s CPU limit differs. The 0.5 CPU runs were replaced, so their numbers are from
this file's previous version and `web/docs/backend-throughput-notes.md`.

| Run | Metric | `web` 0.5 CPU | `web` 2 CPU | Gain |
| --- | --- | --- | --- | --- |
| Base, 1280, 3 workers, threshold 0.35 | Drain | 1,635 img/min | 1,857 | +14 % |
| | End-to-end | 917 | 1,291 | **+41 %** |
| YOLO26n, 1280, 3 workers, threshold 0.15 | Drain | 1,528 | 1,982 | +30 % |
| | End-to-end | 869 | 1,382 | **+59 %** |
| YOLO26n, 1280, autoscale 0→3 (threshold 0.15 → 0.17) | End-to-end | 1,020 | 1,470 | **+44 %** |
| YOLO26n, 1280, autoscale 1→3 (threshold 0.15 → 0.17) | End-to-end | 995 | 1,495 | **+50 %** |

The engine's processing time per image is the same in all of them, so the gain is all outside the model. `web` does two jobs
in one Node process, and both use its CPU:

1. **Receiving uploads.** One HTTP request per image, kept in memory and written to MinIO and Postgres. For the base model's
   preloaded queue (end-to-end time minus drain time), that phase took about 107 s at 0.5 CPU and about 53 s at 2 CPU.
2. **Recording results.** Every image produces **4 events** from the worker (`DOWNLOADING_INPUT`, `PROCESSING`,
   `UPLOADING_OUTPUT`, COMPLETED), handled strictly one at a time (`messaging.ts`: `for await … await handleEventMessage`):

   | Event | Round trips to Postgres / MinIO | Count |
   | --- | --- | --- |
   | Each of the 3 progress events | `getJob` twice (`handleEventMessage`, `applyJobEvent`), `updateJobState` | 3 × 3 = 9 |
   | COMPLETED | `getJob` twice, `statObject` on the result, `updateJobState`, then `checkAndCleanBatchWhitelist` = `getBatch` + `getJobsByBatchId` (all of the batch's jobs, even with no whitelist) | 6 |
   | **Per image** | | **15** |

   Finishing a job only counts once `web` has written it (`updated_at`), so this lag lands directly in both throughput numbers.

**Why autoscale suffers most:** there, both jobs run at once. The same uploads take 43 s with the workers paused, but 79–108 s
while they process, even at 2 CPU (the upload span of the Fast runs at 640 and 1280).

**An estimate of the cost** (from the 0.5 CPU runs, assuming `web` was at its limit there, as the one `kubectl top` sample
showed: 495 m of 500 m): about 14 ms of CPU per uploaded image plus 18 ms per recorded image, 32 ms in total. So 0.5 CPU tops
out at about 15.6 images/s = **940 img/min** when both happen together, which is where autoscale at 0.5 CPU landed
(866–1,049 img/min).

**It also hid the models:** at 0.5 CPU the small model was 14 % behind the nano at 1280 (1,318 vs 1,528); at 2 CPU the gap is
the real 26 % (1,346 vs 1,812), since processing takes 110 ms vs 64 ms.

Fixes, cheapest first, in `web/docs/backend-throughput-notes.md`: raise `web`'s CPU limit to about 1 CPU (Infra; on the laptop 2
CPU gives the gains above, the lab would not gain much), then fewer round trips per event and handling events concurrently (Web).

### Against deface

deface (CenterFace, v1.5.0) run on the same laptop and images: its own CLI on local files, default threshold 0.2, no pipeline
around it, one process. Accuracy from `engine/training/bench/comparison.md`, at deface's precision so it compares fairly.

| Tool | Speed (img/min) | At face precision 0.64: all faces | Faces ≥ 16 px | Plates |
| --- | --- | --- | --- | --- |
| **Fast, 1280, 3 workers** | **1,812** drain, 1,273 end-to-end | **0.804** | 0.935 | **0.986** |
| **Accurate, 1280, 3 workers** | **1,346** drain, 1,029 end-to-end | **0.827** | **0.946** | 0.976 |
| deface, GPU, full resolution | 614 | 0.723 | 0.930 | not supported |
| deface, GPU, 640×480 | 1,871 | 0.547 (P 0.61) | 0.865 | not supported |
| deface, CPU, full resolution (16 threads) | 294 | 0.723 | 0.930 | not supported |

- **Against deface at full resolution:** Fast gets through 3× as many images and Accurate 2.2×, while hiding 8–10 points more
  of all faces at the same precision, and blurring plates too.
- **Per process it's about even.** One worker does 450–600 img/min, about what one deface process does on the GPU (614). The
  gain comes from running 3 workers on one GPU, and our numbers include what deface doesn't do: the queue, object storage and
  the database. deface isn't held back by a `web`, so end-to-end is the fair number for a user.
- **deface at 640×480 is as fast as Fast** (1,871), but that's where it loses the most: 0.55 of all faces against 0.80,
  and 0.86 against 0.94 on faces ≥ 16 px.
- **On a CPU** (2 threads, model only, about the lab's case): Fast at 1280 costs 181 ms per image, deface 236 ms, Accurate 455 ms.
  So Fast is about 0.8× deface's cost, and Accurate 1.9×. deface wasn't run through the lab, so this is the only CPU
  comparison between the two. deface's cost also grows with photo size (it runs at full resolution); ours resizes to the
  input size.
- **The earlier deface GPU numbers (265, 581) were wrong as speed numbers:** those were accuracy runs at threshold 0.05 with
  every detection saved. The CPU run wasn't, which is why the GPU looked slower than the CPU.
